Silicon, from the inside out

The shape of
computation.

Why do the CPU, GPU, and neural processor look like different neighborhoods on the same chip?

An interactive explanation · Move the sliders to explore.

Erase the labels on a chip drawing and the boundaries often remain. A handful of large blocks on one side. Long rows of similar units on another. Somewhere else, a dense, almost woven pattern.

It is tempting to think there must be a particular shape for a CPU transistor and a different shape for a GPU transistor. That is not the useful distinction. Digital circuits use a shared repertoire of devices and small circuit cells; what changes is how those pieces are connected and repeated.1

We can understand the big picture by building up the small one. First, we need something much simpler than a processor.

01 / THE BUILDING BLOCKS

Repetition makes a texture.

A tiny circuit can invert a signal, choose between two inputs, or hold a value. Chip designers have libraries of these standard cells. Many are designed to fit into rows of a common height, even though different functions need different widths.12

Below is a deliberately simplified placement of circuit cells. Switch between a varied collection and a repeated memory cell, then pull back.

Notice that “irregular logic” is not a heap of randomly placed transistors. It still follows a placement grid. Its irregularity is in the mix of functions and connections.

Now repeat one cell. From far enough away, the individual circuits disappear and a uniform patch remains. The regular patch is not a decorative fill: it is what repetition looks like when the details get too small to distinguish.

That leads to the first important trap in reading a chip drawing: a very regular region does not necessarily do lots of arithmetic. It may simply remember lots of things.

02 / KEEPING A BIT

Memory wants to be a grid.

Let our circuit remember one bit: a 0 or a 1. A common SRAM implementation uses six transistors, although other cell designs exist. Repeat the cell and we get an array of stored bits.3

But we also need to reach a particular bit. Sharing a row-selection wire across a row, and bit lines along columns, gives the array an economical structure. A decoder selects a row; peripheral circuitry selects, reads, and writes data.4

Slide through the addresses below. Watch the selected row and column meet. Change the stored bit, move away, and come back to it.

The cells make the dense central rectangle. The supporting circuits form strips around it. Larger memories can be divided into repeated banks, introducing another level of repetition.34

This is why the gold regions in our imaginary chip are so important. Some are caches. Some hold registers or buffered data. Storage accompanies the computation; it is not confined to one “memory corner.”568

A stripe inside a GPU region may be a register file or cache—not a row of shader arithmetic units. The enclosing block and the texture inside it describe different levels of the design.

03 / ORGANIZING DIFFERENT WORK

A CPU needs more than arithmetic.

Suppose we build an adder. It can produce a sum, but it cannot decide which instruction to run next, whether its inputs are ready, or where the result belongs.

A high-performance CPU core has machinery for fetching and decoding instructions, tracking dependencies, scheduling work, accessing memory, and committing results in the correct program order. The open-source BOOM core provides a concrete example of this organization.5

Move through the conceptual stages below. We are following responsibilities, not counting clock cycles.

The arithmetic units are only part of this picture. The rest helps them do useful work while preserving the behavior the program expects. Different responsibilities require different structures, so the inside of a core becomes a mixture rather than one huge repeated arithmetic array.5

Yet there is repetition here too: similar execution units, storage arrays, and—when we step back—entire copies of a CPU core.

A CPU can be heterogeneous inside and repetitive outside. Keep that distinction in mind as we move to the GPU.

04 / REPEATING THE WORKERS

What happens when the work repeats?

Imagine we have the same independent calculation to perform on 64 values. Instead of building 64 completely independent CPU-like front ends, we can organize multiple execution lanes into groups that share instruction issue.

That is a useful route into GPU organization. NVIDIA’s documented hardware model, for example, groups execution resources with local registers, shared memory, and caches in streaming multiprocessors; the GPU contains many such groups.67

Add groups below, then run the jobs. Each group in our tiny model has four lanes. Notice what gets copied along with those lanes.

We have not merely duplicated some multipliers. We have duplicated a working group: instruction handling, registers, local storage, and execution resources. That repeated bundle is what can produce a recognizable large-scale rhythm in a GPU region.6

Nor have we removed control. GPU execution still has scheduling and data-dependent behavior; shared instruction issue is most efficient when the participating threads follow the same path.7

The toy’s arithmetic is straightforward: 64 jobs divided by 8 lanes needs 8 ideal issue rounds. With 32 lanes, it needs 2. The real lesson is not the speed ratio. It is that parallelism gives us a reason to stamp out the same compound structure repeatedly.

05 / ARRANGING THE DATA FLOW

Let the numbers travel.

Now suppose the work is more specific. We want to multiply matrices. Each output is a sum of products: multiply pairs of values, then add those products together.

Cij ← Cij + Aik × BkjOne multiply–accumulate, often shortened to MAC.

Instead of fetching every operand separately for every operation, we can arrange arithmetic cells so neighboring cells reuse values as they pass by. A systolic array is one concrete design that does this; Google’s TPU is a documented example.89

Below, A values enter from the left and move right. B values enter from above and move down. Each square keeps one output’s running sum. Press play, or advance one step at a time.

Look at the geometry we have earned: repeating arithmetic cells connected mostly to nearby neighbors. The grid follows the chosen dataflow, rather than a rule that “AI hardware must be square.” The short local connections are part of the point.9

The array still needs input buffers, output storage, control, and support for other operations. A complete neural processor is more than the grid. TPU documentation, for instance, describes matrix, vector, and scalar units together.8

Not every NPU uses this arrangement, and GPUs can also contain matrix-multiply hardware. This demonstration explains how regular compute geometry can arise; it does not identify the microarchitecture in the example image.7

06 / THE COST OF DISTANCE

Moving a rectangle changes the circuit.

So far, we have talked as though the blocks could be packed wherever they fit. But every connection between them is physical.

Try moving the memory farther from the core. The function of the blocks stays the same. The wire does not.

For this simple model, resistance and capacitance both grow with length. Their product grows with the square of length. Double the wire, and the unbuffered wire-delay term becomes four times as large. Charging the extra capacitance also costs energy.10

Real designers can insert repeaters, use different metal layers, widen wires, or pipeline a connection. Those choices change the delay model, but do not make distance free.10

Physical-design tools therefore consider more than whether rectangles fit. Their objectives include wire length, timing, placement density, and routing congestion. The documented OpenROAD flow exposes these tradeoffs directly.1112

The floorplan is part of the electrical design. The arrangement both reflects the architecture and influences what the architecture can achieve.

07 / WHAT THE SURFACE HIDES

A chip is not a flat drawing.

There is one more reason not to read every visible line literally: integrated circuits have layers. Local connections, longer routes, and power distribution occupy metal above the devices.13

Separate the schematic stack below. Our functional blocks are at the bottom. The patterns above them belong to connections and power, not additional processor cores.

This is the distinction between an architecture diagram describing functions, a floorplan describing placement, and a die image showing a physical surface. They are related views, not interchangeable evidence.61113

A careful reading asks two questions before identifying a block: What level of the design am I looking at? And what kind of image is this?

08 / BACK TO THE BEGINNING

Now look at the example image.

The presentation graphic in the example image uses large compartments, repeated strips, and arrays of smaller motifs. Those are the visual ingredients we have just built.

Example image, cropped to the chip illustration.

But the image alone does not tell us that every visible rectangle is a core, that every stripe is an execution lane, or that the depicted boundaries exactly match manufactured silicon. We should not invent that mapping.

The more useful way to read it is to ask what could have produced each kind of repetition: a stored bit, a group of arithmetic lanes, a complete compute tile, a memory bank, or an entire CPU core. Then use actual documentation or physical evidence to distinguish those possibilities.

Different work creates different structures.
Repeating those structures creates a texture.
Connecting them creates a floorplan.

That is why the regions can look different—even though they belong to the same chip.
